**Rule.** A browser check of a branch (the city tour, an agent's before/after shots, a perf A/B) runs the branch's OWN tile-worker code. The viewer always loads the committed `viewer/tileWorker.bundle.js`, and only `tools/merge.mjs` rebuilds it, after the merge, in the main repo (rule 12). So `tools/tour/serve.mjs` builds the served checkout's `viewer/tileWorker.js` in memory (`tools/tour/freshBundle.mjs`: the same esbuild settings and hash stamp as `tools/build_worker.mjs`) and serves that at `/viewer/tileWorker.bundle.js`; nothing is written into the worktree. Its start-up line says whether the committed bundle is stale. `--committed-bundle` serves the committed file (to reproduce what the live site draws). Job agents serve their worktree for browser checks with `tools/tour/serve.mjs --root <worktree> --port N` (or another server that does the same), never a plain static server, when the branch touches anything the worker imports.

**Why.** The tour of claude/parking1 (2026-11-22) and the first tour of claude/lanes5 (2026-11-23) were served from their worktrees with foundation's committed bundle: parking places and lanes are built in the tile worker, so the tours showed foundation's tiles, and "22/22 ok" said nothing about the branches' own changes. It surfaced when claude/allocrate's tour was compared with parking1's images: a parked van that "appeared" in allocrate was already on foundation since the parking1 merge rebuilt the bundle (claude/allocrate proved it in-page: 0 batch/car mismatches, the same van on foundation). lanes5's sources hashed d0dc19f5003dadf0 while its committed bundle was bbf73c8dffc3edd5.
