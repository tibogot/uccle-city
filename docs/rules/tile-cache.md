**Rule.** A gate row builds a tile with the tile worker's code in node only through the gate's tile cache (`tools/gate/tileBuild.mjs` `tileData(entry, base)` in place of `buildTileData`, or `tools/gate/tileCache.mjs` `cached()` for another builder). The cache key is content: the import closure of the builder's code (for the worker, the closure of `viewer/tileWorker.js`, the same files `tools/build_worker.mjs` bundles and `tools/merge.mjs` hashes), the canonical build options, the node version, the browser stand-ins the build sees, and every file the build read, folder it listed and existence it tested, recorded while it built and re-hashed at every lookup. Only plain data is stored (no function, no class instance); what a row needs of the live objects (keepNet's `net`, `hm`) is kept as plain data by name and any other part throws. A build an input of which changed while it ran is not stored. Writes are a temp file + rename; the cache is capped (`TILE_CACHE_MB`, 4096) with LRU eviction; `--no-tile-cache` (mergeGate or a row) or `TILE_CACHE=0` turns it off, `TILE_CACHE=verify` builds every hit fresh too and throws on a difference.

**Why.** A full gate built the same 120 tiles ~4.8 times (the road stage ~579 builds) in rows that each rebuilt them from data/tiles; a `--changed` gate on a tile-core change took ~35 min. A cache that can serve a tile built from older code or data would pass a gate that the fresh build fails, so correctness comes first: content keys rather than timestamps or branch names, the inputs recorded rather than listed by hand, the code key checked against esbuild's own list of the bundle's inputs, a byte-for-byte comparison of cached against fresh builds in every gate that touches the tile core, and the tracer (tools/gate/trace.mjs) still seeing every input on a hit so the memo and `--changed` keep the true dependencies (claude/tilecache, docs/SPEED_PLAN.md job 8).
