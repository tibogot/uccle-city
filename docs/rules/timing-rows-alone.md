**Rule.** A gate row's timing verdict is never a single read on a machine that may be busy. (1) Every timing verdict is marked `timed(ok)` and the row exits `gateExit(fails)` (tools/gate/timing.mjs): exit 75 when the only failures are timing verdicts, 1 for any other failure. (2) `tools/audit/mergeGate.mjs` runs the timing rows first, alone, one at a time (as before: stutter, stutter2, allocbudget and the other `timing: true` / `alone: true` rows), and re-runs a row that exits 75 alone up to 3 more times, 5 s apart (tools/gate/retry.mjs). A structural row with a calibrated timing check inside (pedsgraph W6, pedssim S4) can stay in the parallel group: its exit 75 is re-run alone after the parallel phase, with the same 3 retries. A row fails when every run failed; a structural failure (exit 1) or a timeout is never retried. (3) A timing budget is calibrated in the same process right before and after the measurement (`measure()` / `slowdown()`: budget x k), and any extra noise margin is a named constant with its measured why (props `COST_NOISE` 1.25). (4) A timing is never read from a cache: a row times the step itself on the tile's own inputs (pedsgraph W6 re-runs buildWalkGraph, the best of 3, and checks it built the same graph), never `d.times` of a tile the gate cache may have served. (5) `GATE_SLOW=<name>` (`slow(name, t0)` at the end of a timed block) makes that path `GATE_SLOW_X` times dearer: the self-test's real regression.

**Why.** On 2026-11-25/26 three structural rows' timing reads blocked about 6 merges. pedsgraph's W6 "walk graph <= 800 ms" read the time stored WITH the cached tile (rule tile-cache): one build under load (809 / 908 ms; ~430 ms fresh) failed it on every later run, whatever the code. trafmix's "sim cost" came back TOO NOISY whenever a tour, another gate or Blender ran. props' "24 awake bodies < 0.1 ms x k" read 0.32 against 0.27: k comes from a tight in-cache loop, and the solver lost more to a neighbour's load than the loop did (0.118 ms / k under load against 0.049 ms / k alone). The timing group already ran alone and first, but a load from OUTSIDE the gate still lands on one read, and one read was the verdict. A burst of other work is short; a regression is on every run. So the verdict is: any one of 4 runs alone within the calibrated budget. A path that really got dearer is over budget on all 4 and still fails (the `timingretry` row proves it with a path made 4 x and 8 x dearer).
