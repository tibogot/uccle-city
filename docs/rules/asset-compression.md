**Rule.** Every file the live site sends goes out compressed or is already compressed inside. A compressible type (glb, bin, json, u16, ... `BR_EXT` in tools/asset_hashes.mjs) gets a brotli-11 sibling `<file>.br` from the Vercel build (`node tools/asset_hashes.mjs`, env VERCEL=1; content-addressed cache in `.vercel/cache/assetbr`), listed in `/asset_hashes.json` `br` (path -> raw size) and served with `Content-Encoding: br` (vercel.json; tools/tour/serve.mjs does the same). The service worker fetches the sibling and answers with it only if the decoded bytes have the listed size AND the content hash; anything else (the CDN re-encoding it, no sibling, an old copy) answers the plain file and turns the siblings off until the next page load. Its answers for a listed file carry ETag `"h-<content hash>"` and it answers that file's HEAD from the list, so the tile cache's dependency tags stay consistent. Without the service worker (the first requests of a first visit, `?sw=0`, a local server with no list) the plain files are served exactly as before; `?assetbr=old` turns the siblings, the `?v=` handling and the hash tags off. A new data type must be added to `BR_EXT` or shown incompressible (the gate measures it); a KTX2 must be zstd- or BasisLZ-supercompressed, because Vercel sends `image/ktx2` raw. Never ship a file as `<name>.glb` with compressed bytes inside or a `Content-Encoding` on a plain path: a client or CDN that does not decode it breaks.

**Why.** docs/PERF_RESEARCH_2026-11.md idea 1 assumed Vercel sent glb / bin / u16 raw. Measured on the live site on 2026-11-22 (node, `Accept-Encoding: gzip, br`), that was wrong: Vercel already brotli-compresses them on the fly, at about brotli level 3 (E4 buildings.bin 461,136 B against brotli-3's 461,141 B). Only image/ktx2, the images and the wav files go out raw, and ours are already compressed inside. So the doc's build-time gzip plus `DecompressionStream` plan would have saved about 2 % (gzip-9 is no better than Vercel's brotli-3). What does save bytes is the level: brotli 11 is 24-37 % smaller than what Vercel sends. On the cold boot's own request list (397 files in the first 33 s) that is 144.6 -> 132.8 MB at today's coverage. With the tiles' `?v=` files also going through the worker, the local 50 Mbit/s stand-in measured 118.3 -> 96.0-96.5 MB before the cover. The bytes are only trusted after a hash check in the worker, because a pre-compressed file sent with a hand-set `Content-Encoding` cannot be tested on a protected preview, and the CDN could legally re-encode or strip it: the check makes the worst case one wasted file, never a broken model (claude/assetgz).
